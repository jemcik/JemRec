Two separate questions, two different answers. Recorded together because
conflating them is what makes this state look unrecoverable when it is not.


A. CAN THE ADB TRANSPORT WORK WITH WI-FI OFF?   No. Definitively.

$ svc wifi disable
$ ip -4 addr show wlan0
wlan0: no IPv4

$ settings get global adb_wifi_enabled
0                         <- reset ITSELF. Was 1 before Wi-Fi went down, and
                             did NOT come back when Wi-Fi returned.

$ ss -ltn
LISTEN  [::ffff:127.0.0.1]:43337
LISTEN  [::ffff:127.0.0.1]:40523
                          <- adbd's *:42321 TLS listener is GONE. Not moved,
                             not rebound to loopback. Gone.

App's existing connection, immediately after:
  exec failed: connect() must be called first

The remedy the brief proposed is not available at this privilege level:

$ setprop service.adb.tcp.port 5555
Failed to set property 'service.adb.tcp.port' to '5555'.
$ getprop -Z service.adb.tcp.port
u:object_r:adbd_config_prop:s0

The shell UID may not write that property, so adbd cannot be pinned to a fixed
port and the "loopback survives because the port is stable" plan is dead as
written. USB would work and defeats the point; Wi-Fi-only would mean recording
only at home.


B. CAN A SHELL-PRIVILEGED CHANNEL WORK WITH WI-FI OFF?   Yes.

ADB does not have to be the RUNTIME transport. It only has to start something.

Measured: a process spawned from an adb shell outlives the adb connection.
  $ nohup sh -c '...' &     # adb session then exits
  alive 1 2000
  alive 2 2000              <- still running, still uid 2000

So a shell-UID daemon is started once over ADB and then stands on its own. The
remaining question is what channel the app may use to reach it. Two candidates
were tested in the same run:

  FAIL abstract:jemrec_probe -> IOException: Permission denied
  OK   tcp:127.0.0.1:28471   -> hello over tcp from uid 2000

SELinux refuses an untrusted_app connecting to the shell domain's abstract
unix socket. TCP on loopback is allowed. A filesystem socket is not a candidate
at all: it would live under /data/local/tmp, which is shell-only and which the
app cannot traverse.

Then the same probe, with Wi-Fi OFF and adbd's listener gone:

$ ss -ltn
LISTEN  [::ffff:127.0.0.1]:28471      <- the daemon, still there
LISTEN  [::ffff:127.0.0.1]:43337
LISTEN  [::ffff:127.0.0.1]:40523

$ ps -A -o PID,USER,ARGS | grep SocketProbe
13076 shell        app_process / SocketProbe

  FAIL abstract:jemrec_probe -> IOException: Permission denied
  OK   tcp:127.0.0.1:28471   -> hello over tcp from uid 2000

The app reached a shell-privileged process with every radio off and adbd not
listening at all.


VERDICT

Wi-Fi off fails for the ADB transport and passes for the architecture that
replaces it. ADB becomes a bootstrap, not a runtime dependency:

  1. over ADB, once, while Wi-Fi is up: start the shell-UID daemon
  2. thereafter: app <-> daemon over TCP 127.0.0.1, no adbd, no mDNS, no network

Cost, stated honestly: a reboot kills the daemon, because processes do not
survive reboots. After every reboot the user needs Wi-Fi and Wireless debugging
once to restart it. That is a real limitation and a far smaller one than
needing Wi-Fi during every call.
